## Implemented protocol capabilities

The 0.3.0 manifest injects only at the top level of HTTPS pages. Discovery grants no account access. The MV3 worker derives the origin from browser sender metadata, checks extension/document/tab identity, and isolates per-document transports. The private local popup binds opener identity, channel, exact website origin and authenticated local session. No seeds, spending keys, cookies or raw signer endpoints enter page code.

Supported wallet methods: `eth_requestAccounts`, `eth_accounts`, `eth_chainId`, `wallet_switchEthereumChain`, exact built-in `wallet_addEthereumChain`, `wallet_revokePermissions`, `personal_sign`, `eth_signTypedData_v4`, and reviewed `eth_sendTransaction`. Read-only additions: `net_version`, `eth_blockNumber`, `eth_getBalance`, `eth_getCode`, `eth_call`, `eth_estimateGas`, `eth_getTransactionReceipt`. Reads require a grant, validate bounded parameters, reject state overrides/custom endpoints and verify RPC chain identity. They cannot submit a transaction.

Network IDs remain **84532, 11155111 and 46630**. Arbitrary RPC addition, mainnet switching and mainnet execution are blocked. Transaction requests use the configured user's ordinary EVM signer, simulation and explicit review; they do not invoke the ZEC relayer. `eth_sign`, private-wallet exports, raw transaction submission and generic third-party `zecone_payWithZec` through the extension remain rejected. Dedicated existing marketplace adapters retain their separately bounded funding path.

EIP-1102 account opt-in and per-origin EIP-155 chain context are preserved. EIP-712 reviews expose domains and effects; signatures can authorize assets and are not treated as harmless login strings. EIP-1271 validation is not claimed for the current EOA. No WalletConnect transport, `wallet_requestPermissions`/`wallet_getPermissions`, arbitrary chain addition, subscriptions or legacy `sendAsync` compatibility is implemented. Clients requiring those capabilities may fail safely. [EIP-1193](https://eips.ethereum.org/EIPS/eip-1193), [EIP-6963](https://eips.ethereum.org/EIPS/eip-6963), [EIP-3085](https://eips.ethereum.org/EIPS/eip-3085), [EIP-3326](https://eips.ethereum.org/EIPS/eip-3326).

The EIP-6963 object stays frozen, announces the actual ZecOne name, and never impersonates MetaMask or overwrites another provider. Local tests verify rejection codes 4001/4100/4200/4900/4901, discovery, origin isolation, account/chain events, revocation, popup closure, session expiry and worker/browser restart. A new test loads the **unmodified production extension** on two intercepted HTTPS fixture origins. This is strong packaging/transport evidence, not a real Uniswap or Sushi connection.

## Reproduction and remaining fixes

1. Use a dedicated Chrome/Edge test profile with extension 0.3.0. Review the new top-level HTTPS content-script scope; there are no broad background host/API privileges or key-export capabilities.
2. Use an explicitly provisioned disposable wallet backend; do not start the historical server merely to obtain screenshots. Its startup can open old databases and run workers. Existing launch scripts are not an isolated Phase 6 live-site environment.
3. Run `npm run test:extension` for packaging/transport checks. Separately inspect each official live picker, select the actual installed ZecOne entry, and review the exact origin/account/network. Do not inject a pretend provider to manufacture detection evidence.
4. Record discovery, actual connected address/network, switch request, harmless understood signing request, safe rejection, revocation and reconnect separately. Stop before accepting unapproved terms or signing asset permissions. Mainnet transaction/switch rejection is an expected policy outcome, not transaction compatibility.
5. Inspect `eth_sendTransaction` handling only on supported testnets with exact user authorization. No dApp calldata becomes eligible for ZEC sponsorship by connecting.

Remaining blockers: extension-enabled computer-use surface and disposable backend deployment for actual cross-site approvals; per-site testnet support; API credentials where a catalog requires them. This phase does not claim universal website compatibility or new real-chain settlement evidence.
