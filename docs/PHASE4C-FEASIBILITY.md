## Genuine protocol deployment

The official [Seaport repository deployment table](https://github.com/ProjectOpenSea/seaport) lists Seaport 1.6 on Base Sepolia at `0x0000000000000068F116a894984e2DB1123eB395`. Read-only RPC confirmed chain 84532, 23,981 bytes of deployed code, runtime hash `0x7912af42062ec0080cde88360c1429d58984ae16eb3f17af505b815bf6ffc745`, version `1.6`, controller `0x00000000F9490004C11Cef243f5400493c00Ad63`, and the independently calculated chain/address-bound Seaport domain separator. See [preflight](phase4c-evidence/seaport-preflight.json). This is the existing public contract; no modified Seaport deployment will be described as official.

The official [interface](https://docs.opensea.io/docs/seaport-interface) provides `fulfillAdvancedOrder(advancedOrder, criteriaResolvers, fulfillerConduitKey, recipient)`. A FULL_OPEN (type 0), single ERC-721, fixed native-ETH listing can be fulfilled in full with numerator/denominator 1/1 and a separate user recipient. The provider pays ETH while Seaport transfers directly from seller to user. Use empty criteria/extra data, zero zone/hash, and zero conduit keys with direct seller approval to Seaport. Reject partial/restricted/contract orders, criteria, bundles, dynamic amounts, ERC-20 payment, tips and unknown consideration recipients. No temporary NFT custody is needed.

Orders require canonical hash comparison through `getOrderHash`, EIP-712 seller signature verification (or authoritative onchain validation), current counter/status, owner and approval checks, exact consideration sums and simulation. Seller signatures do not alone prove present availability. Order cancellation, ownership/approval changes or a competing fill during ten Zcash confirmations must stop execution and preserve recovery liability.

## Dependencies and execution boundary

Official [seaport-types](https://github.com/ProjectOpenSea/seaport-types) npm version **1.6.3** provides the Solidity structs/interfaces. Pin this exact dependency and its lockfile integrity; retain Solidity 0.8.28, OpenZeppelin 5.6.1 and viem 2.57.4. Official [seaport-js](https://github.com/ProjectOpenSea/seaport-js) version **4.3.1** was inspected; its recipient-directed fulfillment path agrees with the protocol interface. Its ethers SDK is not required: existing viem can hash/sign the documented structs and encode the narrow call. Do not accept arbitrary SDK/API transaction bytes.

A new immutable ZecOne executor will pin protocol/runtime, collection, provider, seller policy and consideration policy. The separate `SEAPORT_PURCHASE` signature binds exact order components, Seaport version/hash, recipient, calldata, max value/gas, payment/refund terms, expiry and nonce. Existing historical signatures stay unchanged. Reuse the shared purchase journal, per-chain reservations, native payment UUIDs, ten-confirmation scans, signed-before-broadcast persistence and manual recovery. The contract verifies recipient delivery atomically; receipt checks additionally require Seaport fulfillment, NFT Transfer, consideration and consumed state.

## OpenSea API versus protocol

Official [API authentication documentation](https://docs.opensea.io/reference/api-keys) describes API keys, an optional instant free-tier key, expiring credentials and response-provided rate limits. Never hardcode the illustrative rates: honor `Retry-After`/`X-RateLimit-Reset`, cache reads and stop on authorization failure. No existing API credential was found in the configured local path/environment. Keys, if supplied, must stay local and must never include Zcash keys or viewing data.

Current [API changes](https://docs.opensea.io/changelog/removing-deprecated-rest-api-endpoints-and-response-fields) remove the old GET orders/listings endpoint in favor of collection listings and individual order lookup. Official [fulfillment data](https://docs.opensea.io/reference/generate_listing_fulfillment_data_v2) is a read-like POST returning proposed order/transaction data, not authority to execute it. Any response must match chain/protocol/order/recipient/value and independently reconstructed calldata. Unexpected added fees/tips are rejected.

Observed access: the production `/api/v2/chains` endpoint returned HTTP 200 and no Base Sepolia entry; the historical `testnets-api.opensea.io` host failed to connect. [Access evidence](phase4c-evidence/opensea-access.json) records the exact observations. These do not prove a universal API outage, but do not establish available testnet listing discovery. Build a read-only adapter that fails closed on unsupported chains/access and exercise validation with explicit fixtures. The authorized live fallback is a controlled seller-signed Seaport listing, not an OpenSea-hosted/API listing. No mainnet purchase or listing publication is authorized.

## Website transport

OpenSea's [wallet connection guide](https://support.opensea.io/en/articles/8866951-how-do-i-log-in-to-opensea-with-a-web3-wallet) requires selecting an available wallet provider and following its connection/signature prompts. ZecOne currently exposes an opt-in popup SDK to cooperating dApps. It does not inject an extension provider into OpenSea and has no WalletConnect transport. EIP-1193 methods and EIP-6963-compatible discovery in a cooperating page are insufficient for arbitrary website discovery. Direct OpenSea website compatibility is untested and not claimed. Future work needs an actual browser-extension EIP-1193/EIP-6963 transport or compatible WalletConnect implementation, origin permissions, supported signature/chain-switch flows and a separate end-to-end website test. No wallet security or authentication bypass is proposed.
