# Phase 4B security boundaries

This is a local, testnet-only trusted payment processor. Zcash Testnet payment attestation comes from the existing pinned NU7 wallet scanner and trusted lightwalletd. The EVM contract does not verify Zcash consensus. User and provider keys remain in separate existing local files; no key migration occurs. Only the local user signing helper reads the user EVM key. Provider execution uses its own ETH; it never requests user token allowances.

The new `ZecOneExecution` EIP-712 domain version 1 and immutable executor address separate token swaps from historical NFT signatures. The signed action binds source network, destination chain, random order ID and nonce, recipient, provider, adapter, router target, native amount, gas budget, ZEC payment, expiry, parameter hash, exact calldata hash and refund destination hash. Parameter hashing binds WETH input, amount, token/decimals, router, route, expected/minimum output, slippage, deadline and reference block/hash. Only TOKEN_SWAP is executable. Future-marketplace interfaces have no signing or execution endpoint.

The immutable Base Sepolia executor admits one router, pool and fixed-supply test token. It rejects wrong-chain/provider/recipient, altered parameters, replay, expiry, extra native spending and output below the approved minimum. It checks the actual recipient balance delta during the router call against returned output, so a transfer tax or wrong delivery reverts atomically. A reentrancy guard prevents callback reentry. No arbitrary calldata, router override, ERC-20 input allowance or generic fallback is exposed. The router wraps provider ETH into WETH and swaps through the real pair.

Read-only checks verify runtime-code hashes, router factory/WETH, factory pair mapping, token decimals, token orientation and reserve/balance equality. Quotes use one reference block and reproduce the router's fee-adjusted constant-product result. Input is capped at 0.0002 test ETH, price impact including pool fee at 300 bps, and user slippage at 1–300 bps. Native/executor simulation repeats before Zcash payment and before EVM signing. A simulation is an observation, not a token-safety guarantee or output guarantee during confirmation delay.

NFT and swap requests use the same SQLite reservation ledger. Per-chain aggregate reservation includes both action kinds. The balance read and reservation acquire the shared service lock; SQLite immediate transactions enforce aggregate limits. Unresolved destination nonces block later work on that chain. Legacy mint/action workers see swap reservations through the existing reservation gate. Native address allocation, stable payment UUIDs, ten-confirmation scans, expiry/reorg handling and durable signed-before-broadcast persistence are reused. Historical signed intents and prior proof files are not rewritten.

Completion requires a canonical receipt at Base's three-block policy, exact executor event, actual pair Swap/Sync and output-token Transfer events, exact provider/target/value/calldata, consumed digest and the recipient's balance increase recorded atomically by the immutable executor. Receipt-block state is checked. Later user transfers do not invalidate the historical executor balance delta. Any mismatch, price/slippage failure or uncertain broadcast preserves payment liability and a manual recovery record. No automatic refund is implemented.

Browser APIs retain local Host/Origin, authenticated HttpOnly session, CSRF and ownership checks. Quote approval and native Zcash payment approval are separate. There is no external dApp method exposing swap payment details. The token panel displays the exact contract, route, amounts, deadline and simulated rate. A provider can correlate shielded payment with public token receipt. Same-user Windows malware can read local files; signer processes are not hardware isolation.

No independent audit is claimed. Historical upstream V2 audits do not audit this integration. Base L1 data fees can vary independently of execution gas; the signer bounds execution gas/fee and reserves a conservative L1 allowance, not a consensus-enforced cap on all future fee conditions. The user's signed ZEC price cannot increase silently; excess provider gas risk belongs to the provider.
