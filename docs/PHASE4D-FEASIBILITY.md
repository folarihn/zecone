## Findings and chosen boundaries

The existing EIP-1193/EIP-6963 SDK opens a cooperating website's popup. It is not injected into unrelated websites. The local popup authenticates browser-supplied `MessageEvent.origin` and `source`, binds a random channel to a locally paired session, and requires visible account/signing approval. It exposes no Zcash RPC. All localhost HTTP APIs retain Host, Origin, session and CSRF checks.

OpenSea's [wallet support guide](https://support.opensea.io/en/articles/8867089-what-crypto-wallets-can-i-use-with-opensea), reviewed today, documents EIP-6963. Actual `https://opensea.io/` displayed MetaMask, WalletConnect, Phantom, Robinhood and More Wallet Options. This proves available choices, not ZecOne connectivity. The available controlled browser is an in-app browser without an extension installation interface. No extension will be silently installed. A real website connection therefore remains gated on a user-installed extension in an accessible Chrome/Edge profile, browser popup/COOP compatibility, and explicit account approval. OpenSea presents terms at connection; automation cannot accept them without action-time confirmation.

Choose a minimal Chromium Manifest V3 injection package, with no background signing privileges or localhost HTTP access, reusing the existing origin-authenticated popup protocol. MAIN-world code is public and untrusted, not a secret or privileged extension authority. The signer trusts the browser's opener/source/origin and local approval, never a webpage-provided origin string or extension claim. Only exact OpenSea origins are in the distribution manifest. An isolated local browser harness tests this transport; it cannot establish real-site compatibility. If the actual site's opener isolation blocks it, report the blocker rather than weakening browser security. See [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) and [messaging security](https://developer.chrome.com/docs/extensions/develop/concepts/messaging).

WalletConnect is visible on OpenSea, but the [maintained WalletKit repository](https://github.com/reown-com/reown-walletkit-js) requires a registered relay project ID and wallet-side session implementation. There is no configured project ID. It adds external relay/session infrastructure and is not selected. Old Reown web usage documentation URLs now return 404; do not infer an SDK method from them.

## Genuine API access

The [official key guide](https://docs.opensea.io/reference/api-keys) and [instant issuance reference](https://docs.opensea.io/reference/create_instant_api_key) document POST `/api/v2/auth/keys`. The user's explicit Step 5 authorization was verified after an initial automatic approval rejection. The same request then succeeded. Credential is only in ignored `.secrets/opensea-development-key.json`. Actual expiry: `2026-10-20T10:27:38.767069775Z`; actual limits: reads 600/hour, writes 30/hour, fulfillment 5/minute. Do not print the key or rely on these rates for future keys. Honor response retry/reset headers and stop on expired/denied credentials. No wallet seed or spending key is needed.

Authenticated calls successfully returned `/api/v2/chains`, ten actual Pudgy Penguins listings, and recipient-directed fulfillment data for Ethereum order `0x1c01aa564f5d306efd35ca896ad9924c12f470af3c015f459ace8637961036a0`. These are discovery/preparation observations only; independent chain/signature validation is still required. Listing discovery omits the seller signature; fulfillment preparation supplies it. Salt can be hex while other uints are decimal; normalize strictly without JavaScript precision loss. Observed fulfillment protocol label is `seaport1.6`, with a four-byte attribution suffix. Do not assume the old adapter's `seaport` label describes current API responses.

Official endpoints checked:

- [Collection listings](https://docs.opensea.io/reference/list_listings_collection_all): GET `/api/v2/listings/collection/{slug}/all`.
- [NFT metadata](https://docs.opensea.io/reference/get_nft): GET `/api/v2/chain/{chain}/contract/{address}/nfts/{identifier}`.
- [Fulfillment preparation](https://docs.opensea.io/reference/generate_listing_fulfillment_data_v2): POST `/api/v2/listings/fulfillment_data`, supplying listing, fulfiller and explicit recipient. This generates data, not a transaction broadcast.
- [May 2026 API removals](https://docs.opensea.io/changelog/removing-deprecated-rest-api-endpoints-and-response-fields): use current collection endpoints and individual order lookup; do not expect the old order wrapper.

## Validation and non-executing preview

Keep the Phase 4C execution policy unchanged: Base Sepolia only, controlled immutable wrapper, zero conduits, full-open fixed-price native ETH/single ERC-721. Genuine mainnet listings are handled by a separate read-only public client with no signer, wallet client, Zcash allocation, reservation or execution route. Initially support Ethereum inspection only. Other networks fail closed.

Read-only inspection may validate FULL_OPEN listings with zero zone/hash and either direct approval or the observed OpenSea conduit. Verify conduit derivation, runtime and open Seaport channel through the canonical controller; never just trust an API-supplied operator. Independently check protocol bytecode/version/domain, order hash/counter/status, seller signature or onchain validation, ownership, approval, exact fixed consideration/fees and expiry at one canonical block. Check API asset/price and reconstruct `fulfillAdvancedOrder` including recipient, original consideration, signature, conduit and bounded attribution. Reject restricted orders, criteria, bundles, partials, dynamic prices, ERC-20 consideration and unsupported signatures/routes. See [Seaport deployment repository](https://github.com/ProjectOpenSea/seaport), [models](https://docs.opensea.io/docs/seaport-models), [interface](https://docs.opensea.io/docs/seaport-interface) and [conduit controller](https://docs.opensea.io/docs/seaport-conduit-controller).

Simulation may override only the public prefunded-provider address's hypothetical ETH balance, clearly labeled; no real mainnet funding or signing. Report failure rather than infer execution success. Preview binds order hash, recipient, chain, consideration and expiry; displays source, image/collection, exact price/fees, estimated gas/liquidity and the existing explicitly simulated 1 TAZ = 0.02 ETH conversion. No payable address or approve/pay button is generated. Mainnet orders cannot be attached to the testnet settlement worker. Preview expiry is at most five minutes and before listing expiry; refreshing requires fresh verification. OpenSea attribution is retained only in read-only reconstructed simulation, not introduced into the existing execution adapter.

Collection metadata is an API assertion, not an onchain fee registry.
