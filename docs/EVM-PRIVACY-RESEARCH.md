# EVM privacy research

Reviewed 15 October 2026. Research only: no privacy contracts deployed, no mainnet transactions and no new SDK installed. Estimates below are engineering judgments, not measured performance or guaranteed delivery dates.

## Threat model and vocabulary

Zcash shielding protects payment contents on the Zcash ledger. It does not prevent the merchant verifier from learning its own incoming payment, or hide the public EVM settlement, recipient, NFT ownership, router logs, quantities or timing. The current operator can join payment/order/execution records. RPC providers, websites and analytics may also link IPs, cookies, connected accounts and transaction timing. A compromised local OS can access this development wallet; physical signer isolation remains unvalidated.

Private funding, private transfer, private recipient, private ownership, private execution and unlinkability are separate properties. A fresh public recipient can reduce association with a primary account while its assets and actions remain completely public. An NFT's uniqueness makes inference particularly difficult to prevent.

| RAILGUN                         | Private pool transfers; public shielding/unshielding boundaries | Private holder inside pool; contract custody publicly visible               | External DEX/market calls remain observable                 | Ethereum/Polygon/BNB/Arbitrum documented; Base and Robinhood support not established by this review |
| Aztec                           | Private notes and contract state within its own rollup          | Private ownership possible for an application designed for that environment | Mix of private client execution and public rollup execution | Separate Ethereum L2; not an EVM plugin on Base or Robinhood                                        |

ERC-5564 standardizes stealth derivation and announcements; it is not an anonymity system or private EVM. Publishing a primary-account-funded gas transfer to the destination can undo the benefit. Separate scanning/viewing keys and recipient recovery are necessary. [ERC-5564](https://eips.ethereum.org/EIPS/eip-5564).

RAILGUN's developer docs describe private transfers and Relay Adapt composition. The SDK flow for cross-contract calls unshields into the adapt contract, executes calls, then reshields outputs in one transaction. Public DEX prices, asset identifiers, call traces and block timing still leak information. This is not evidence that our Seaport adapter works unchanged. [Cross-contract calls](https://docs.railgun.org/developer-guide/wallet/transactions/cross-contract-calls), [transaction model](https://docs.railgun.org/developer-guide/wallet/transactions).

The documented NFT path supports ERC-721; its NFT guide explicitly excludes ERC-1155. A public ERC-721 entering custody remains identifiable as that token. Pool custody can conceal the beneficial holder, but cannot erase a unique token's public history. Unshielding to a primary wallet exposes ownership again. [Shield NFTs](https://docs.railgun.org/developer-guide/wallet/transactions/shielding/shield-nfts), [private NFT transfers](https://docs.railgun.org/developer-guide/wallet/transactions/private-transfers/private-nft-transfers).

The official RAILGUN getting-started page currently recommends wallet SDK **10.4.0**, shared-models **7.6.1** and ethers **6.13.1**. These are documentation recommendations, not installed or locally validated dependencies. Its introductory network guide names Ethereum, Arbitrum, Polygon and BNB; do not infer Base/Robinhood support from EVM compatibility. Pin matching contract addresses, circuit artifacts, SDK versions and fee parameters before a future prototype. [SDK setup](https://docs.railgun.org/developer-guide/wallet/getting-started), [network guide](https://docs.railgun.org/wiki/learn/getting-started).

RAILGUN fees must be queried: the setup page describes 25 bps default deposit and withdrawal fees and zero default NFT fee; gas and broadcaster charges are additional. Do not hardcode these as executable prices. Proving, sync and broadcaster availability add latency that has not been benchmarked here. [Provider and fee setup](https://docs.railgun.org/developer-guide/wallet/getting-started/2.-setting-up-networks-and-rpc-providers).

Aztec supports private/public state and client-side private execution through its PXE; applications use Noir rather than deploying our Solidity adapter unchanged. The current official network page lists Alpha/mainnet **5.2.0** and Sepolia-backed testnet **6.0.0-rc.1**, with client/contracts/node versions matched to the selected network. These are observed documentation values, not a claim of operational validation by ZecOne. No native Aztec deployment on Base or Robinhood was established. [Architecture](https://docs.aztec.network/developers/docs/foundational-topics), [current networks and versions](https://docs.aztec.network/networks).

## Answers and recommendation

1. Delivering an NFT without exposing a primary wallet is feasible in principle using a separately controlled destination. Its public owner is still visible. Current fixed-recipient adapters need an explicit new authorization design; backend-generated unrestricted custody is not acceptable.
2. A pool-based swap can conceal the user's balance relationship while the external swap is public. RAILGUN documents this composition. Full private contract execution requires a different environment such as Aztec.
3. Seaport composition needs a dedicated audit: caller/conduit rules, ETH versus wrapped assets, receiver callbacks, atomic reshielding, order validity and protected recipient must all work together. No production compatibility claim is made.
4. Sellers see public fulfillment, consideration and the onchain recipient/custodian. They may infer identity through unique NFTs, external accounts or timing even if a primary address is absent.
5. The current relayer can correlate payment and delivery. A privacy pool added after payment does not automatically remove the operator's knowledge.
6. Pool circuits, proving artifacts, contracts/upgrades, RPC synchronization, broadcaster availability and recipient viewing-key custody add trust and failure modes. Small anonymity sets and distinctive amounts weaken unlinkability.
7. Ethereum has the strongest documented candidate coverage here. Base/Robinhood can use fresh public recipients as a future design, but neither has verified RAILGUN/Aztec settlement support in this project.

Before the hackathon, prioritize a **testnet fresh-recipient design review and local prototype**, estimated 2–3 engineer-days plus 1–2 days for recovery/authorization testing. User-side generation, private ownership proof to the local wallet, and isolated encrypted custody must precede any adapter change. No claim of private ownership or execution. Do not fund its gas from a primary address or publish the primary signature onchain. An ERC-5564 scanner prototype is a separate 3–5 day investigation; it is not implemented in Phase 6.

Longer term, separate payment verification from destination execution, use narrowly scoped authorizations and minimize retained cross-chain mapping. Explore blinded redemption credentials with non-colluding operators, amount/timing protections and independent auditing. This requires cryptographic protocol design; ordinary opaque IDs or hashed order IDs do not provide unlinkability. Keep viewing keys local, request selective disclosure explicitly, separate monitoring credentials from spend authority and define data retention. RAILGUN composition is an estimated 2–4 week investigation plus external review; Aztec application design is a larger multi-week project with different assets/bridging assumptions. These estimates exclude audit scheduling and live infrastructure costs.

No privacy solution is enabled in this phase. Mainnet readiness remains **NO**.
