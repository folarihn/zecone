# Phase 8D.1 — non-executing transaction intents

Checkpoint: `2c9b00d`. Scope: testnets and request inspection only. Connection permission, preview consent, recipient financial authorization and relayer execution authority are distinct. This phase implements only the first two boundaries. Every canonical intent has `executionMode: preview-only` and `executable: false`, including after consent and successful simulation.

## Existing interfaces and demonstrated adapter boundaries

- `extension/inpage.js`, `policy.js`, `background.js` and `content.js`: EIP-6963 discovery and EIP-1193 requests with browser-authenticated origin/document transport. The isolated popup and authenticated API reach `Dapps.request`. No injected wallet impersonation or new provider RPC methods are added.
- `extension/solana.js` and `services/solana/provider.ts`: connection-only Wallet Standard. There are no advertised signing features. The new local inspector is not a dApp signing interface.
- `services/execution/base.ts` and `intent.ts`: Base Sepolia NFT mint accepts an exact recipient-signed `MintIntent` and a privileged prefunded relayer. Its ABI is `mint((address,uint256,bytes32,uint64),bytes)`, with the fixed 1,000,000-zatoshi demo price. Recognizing that ABI does not verify its recipient signature or authorize the mint.
- `services/marketplace/purchase.ts` and `service.ts`: `buy(uint256,address)` shape is recognized at a pinned marketplace. Actual settlement invokes an executor with separately validated listing, seller, NFT, price, origin, quote and user signature. Direct buy calldata cannot replace these checks. Existing testnet adapters cover Base Sepolia, Ethereum Sepolia and Robinhood testnet.
- `services/swaps/intent.ts`, `adapter.ts` and `service.ts`: one Base Sepolia native-input route uses `swapExactETHForTokens(uint256,address[],address,uint256)`. Existing execution validates code hashes, factory, reserves, pool, WETH/output token, quote block, signed financial terms and bounded slippage (1–300 bps). Preview registry limits input to 0.0002 test ETH and a two-token route. Expected output/slippage cannot be inferred from a router's minimum-output field alone; they remain unverified in the preview.
- `services/solana/transactions.ts`, `settlement-model.ts`, `settlement.ts` and `cpmm.ts`: canonical SOL delivery and one Raydium devnet CPMM swap. Delivery fixtures allow 1/2/5 million lamports. Swap is exactly 1 million WSOL units, decimals 9 → 6, 100-bps slippage, pinned pool/program/program hash and calculated positive minimum. Existing settlement separately verifies payment, authorization, claims and finalized effects. It is not called by this inspector.
- `services/wallet/checkouts.ts` and existing relayer policies: private payment associations and financial journals are intentionally excluded from new intent imports and response models.

## Model and registry

`services/wallet/transaction-intents.ts` defines version 1, request ID/digest, origin, destination, operation, target/recipient, input units/decimals, output/minimum, input/fee/rent limits, simulation status/gas, expiry, risk, consent and adapter recognition. Unknown token decimals and unverifiable expected output remain `null`; estimates are never fabricated. No source payment ID, source transaction ID, seed, key or financial order identifier is part of the model.

The EVM registry is operator-supplied, explicit and empty by default. Each entry pins testnet, contract, operation, runtime code hash, maximum input and network-fee cap; swaps additionally pin both route tokens. Duplicate entries, mainnet, foreign mint/swap networks and limits above the existing ceilings are rejected. Supplied addresses are configuration, not evidence of deployment. A decoded method on another address is unsupported. No automatic contract discovery or universal router support exists.

`intent-rpc.ts` performs read-only chain checks, bytecode hashing, `eth_call`, gas and fee estimation. Bytecode and call/estimate reads use the same block number. RPC transport has bounded timeouts and no automatic retries; existing network gas/fee ceilings apply. Simulation facts must match the request digest, chain and configured code hash and be fresh within 30 seconds. Simulation does not verify all marketplace facts, financial signatures, proxy state or economic quote assumptions, and never makes the intent executable. Calls are simulated from the connected user, so relayer-only methods can correctly fail simulation.

## Provider integration and consent

The optional `Dapps` policy `{ intents: IntentReviews }` intercepts `eth_sendTransaction` before the legacy signing client. Request input still passes existing strict transaction/origin/chain validation. The server scope includes authenticated session, browser channel, exact origin, connected account and selected testnet. Review consent binds the exact stored review hash and request digest; revocation, chain changes and expiry fail closed. Cancellation is terminal. Request IDs reserve before async simulation, preventing concurrent interpretations from sharing an ID with different bytes.

Opt-in local server launch: `npm run wallet:dev -- --intent-previews`. Optional `ZECONE_INTENT_ROUTES` points to an operator-maintained public JSON array of `EvmRoute` records. Without it, all calls remain unsupported previews. This flag also disables the legacy sign/send approvals in that server instance. It does not transform the historical wallet server into a keyless process; its legacy Engine and workers remain existing architecture. This phase's tests instantiate the isolated `Dapps` boundary with disposable scopes, never launch that server against live wallets, and never unlock credentials. Ordinary historical launch/settlement behavior is unchanged.

Preview consent is persisted as non-executing review state. `eth_sendTransaction` ultimately receives a clear 4001 non-execution response, never preview JSON masquerading as a transaction hash. The existing approval popup displays operation, assets, raw amounts, recipient, limits, verifiability and trust/privacy disclosures, with a “Record preview consent” button. This is functional review integration, not UI polish or unified financial checkout. Preview identifiers are excluded from the shared legacy request list; details use the scoped request/status path only. Ephemeral review state is bounded to 512 entries per process. On restart, pending preview consent fails closed; users must create a fresh request. A persisted preview marker cannot fall through to legacy signing even if the process restarts without preview mode.

## Restricted Solana inspection

`services/wallet/solana-intents.ts` is a local testing interface, not an HTTP or Wallet Standard signing feature. It reconstructs the complete reviewed legacy message through existing builders before exposing facts. Extra instructions, unknown programs, altered account metas, fee-payer/recipient changes, versioned messages/ALTs, noncanonical encoding, nonzero signatures and incorrect decimals/terms are rejected. Canonical Raydium reconstruction covers two idempotent ATA creations, WSOL funding, sync-native and the exact swap account list. Compute-budget additions are unsupported; the recognized compute budget is the network default, with simulation units reported.

A caller must supply trusted read-only genesis, blockhash/height, route/account-fact validation and simulation implementations. No live Solana connector for this local interface is installed by this phase. Synthetic tests explicitly stub those chain reads and do not constitute new chain evidence. Fee ≤10,000 lamports, rent ≤6,000,000 and total debit ≤7,010,000 are enforced; simulation's estimated fee must match. Blockhash validity is rechecked after simulation. Route callbacks receive destination facts only, with no origin, request ID or source-chain context. Unknown input and nested swap/lifetime fields are rejected.

## Privacy, limitations and next boundary

No new logs, analytics, public URLs, browser storage or financial journal joins are introduced. RPC sees destination calldata, addresses and request metadata; the operator sees local origin/session/request relationships. Destination ownership and activity are public, and timing/amount correlation remains possible. The existing historical plaintext credential limitations and trusted prefunded relayer assumptions remain unchanged. No anonymity or production custody claim is made.

Compatibility is narrow and synthetic at the transaction-intent level. Phase 8D.0's real-site observation remains partial: ZecOne discovery and Uniswap picker visibility were observed; current OpenSea picker/cancellation automation was blocked. No authenticated OpenSea/Uniswap action, third-party transaction execution or end-to-end ZEC-funded dApp flow is newly verified here.

Recommended Phase 8D.2, subject to user authorization: bind one pinned dApp action to fresh adapter-backed quotes and recipient financial authorization, then integrate the existing checkout without leaking source identifiers; provide a trusted live read-only Solana inspection adapter; test origin/session expiry and exact consent in a fixture browser. Broader UI polish and any live signing remain separate scope.
